Types of Roles

Product iOS Developer

Builds consumer-facing iOS applications, focusing on user experience, performance optimisation, and cross-device support (iPhone, iPad, watchOS). Deep expertise in SwiftUI, UIKit, Core Data, and App Store submission.

iOS SDK/Framework Developer

Develops reusable libraries and frameworks that other iOS developers use. Requires advanced knowledge of Swift generics, protocols, access control, and binary compatibility. Strong focus on API design and documentation.

iOS Platform Engineer

Works on iOS infrastructure, tooling, and build systems. Expertise in Xcode Cloud, Fastlane, CI/CD pipelines, and cross-platform coordination. Often bridges iOS development with DevOps.

Swift, Memory Management & App Lifecycle

Master Swift's core concepts, ARC memory management, and iOS app lifecycle states. This section is critical for all iOS roles.

  • Explain the difference between value types and reference types in Swift. Provide examples.
  • What is ARC and how does it prevent memory leaks?
    Interviewer Insight: ARC questions test whether you've tracked down a real retain cycle in Instruments, not whether you can define strong vs weak references. Candidates who've shipped production code mention specific tools—Memory Graph debugger, Allocations instrument—and real scenarios like network callbacks keeping view controllers alive unnecessarily.
    Sample Answer Guidance: ARC tracks strong references to objects automatically; when the count reaches zero, the object deallocates. The limitation is circular references—a closure capturing self while the view controller holds the closure creates a retain cycle preventing both from deallocating. I fix this with [weak self] in closure captures: networkManager.fetch { [weak self] result in self?.updateUI(result) }, allowing deallocation when no external references exist.
  • Describe a retain cycle and show how to prevent it with code.
    Sample Answer Guidance: A retain cycle happens when object A holds a strong ref to B, and B holds a strong ref back to A (often via a closure), preventing both from deallocating. Example: a ViewController strong-references a closure that captures self. Fix with [weak self] capture list: timer.start { [weak self] in self?.updateLabel() } ensures the closure doesn't prevent the view controller's deallocation, breaking the cycle.
  • What are optionals in Swift? Why are they important?
  • Explain Swift protocols and provide a practical example.
  • What are generics in Swift? Provide an example with constraints.
  • Describe the iOS app lifecycle and the key state transitions.
  • What is the difference between strong, weak, and unowned references?
    Sample Answer Guidance: Strong references increase refcount and keep objects alive (use by default). Weak references don't increase count and return nil on deallocation, preventing cycles—ideal for delegate properties: weak var delegate: TableViewDelegate?. Unowned references also don't increase count but assume the object exists; they crash if accessed after deallocation, suitable when the referenced object's lifetime always exceeds the referencing object (e.g., a closure capturing self in a method where self outlives the closure).
What interviewers look for: Evaluators expect clear explanations of ARC, retain cycles, and app state transitions. Candidates should provide real examples and understand the practical implications of memory mismanagement. A strong answer sounds like: 'I once debugged a retain cycle in production using Instruments—a closure was capturing self strongly, and I fixed it with [weak self]. That reduced memory footprint by 40% and stopped crashes on older devices.' A weak answer sounds like: 'Um, ARC is automatic, so the compiler handles memory for you. Strong and weak references... one is stronger? I don't really remember when to use each.'

SwiftUI, UIKit & Architecture Patterns

Compare SwiftUI and UIKit, understand architectural patterns (MVVM, VIPER), and manage state across complex apps.

  • What are the key differences between SwiftUI and UIKit?
  • Explain MVVM (Model-View-ViewModel) architecture in iOS.
  • When would you use VIPER over MVVM? What are the trade-offs?
    Sample Answer Guidance: VIPER isolates concerns across five components: the View renders UI, the Presenter orchestrates logic, the Interactor fetches data, the Entity represents data models, and the Router handles navigation. It's excellent for large teams with strict separation requirements—each developer owns one component. Trade-off: significant boilerplate and overhead for simple features. For rapid iteration or smaller teams, MVVM with Combine is often sufficient and more productive.
  • Explain state management in SwiftUI. What tools are available?
    Interviewer Insight: SwiftUI state management questions reveal whether you have opinions from production experience or just prefer what tutorials taught you. Candidates with real shipping experience discuss performance pitfalls—unnecessary view redraws from overusing @State, or when to switch to ObservedObject to avoid prop-drilling. Beginners treat all state tools as equivalent.
    Sample Answer Guidance: @State is for local, simple state; @StateObject manages complex ViewModel objects with Combine publishers (@Published var users: [User]). @ObservedObject watches external objects without owning their lifecycle. For app-wide state, I use @EnvironmentObject with a Combine-based AppState wrapping @Published properties, passed via .environmentObject() at the root. This avoids prop-drilling and keeps reactive updates clean—the view hierarchy subscribes to publishers and redraws only affected views.
  • How do you handle navigation in SwiftUI versus UIKit?
    Sample Answer Guidance: UIKit uses NavigationController.pushViewController() or present() for imperative control. SwiftUI is declarative: NavigationStack (iOS 16+) replaces NavigationLink, managing navigation state via @State var path: [Route] and a navigationDestination() modifier. For complex flows, I define a Router enum (Route.userDetail(id:)) and bind it to navigationDestination(for:destination:), allowing the app to control navigation from state rather than button taps.
  • Explain Auto Layout and when you'd use it versus SwiftUI.
    Sample Answer Guidance: Auto Layout (UIKit) uses NSLayoutConstraint to position views—powerful but verbose. Managing constraint priority and conflicts requires careful debugging (Xcode shows conflicting constraint warnings). SwiftUI's declarative layout (VStack, HStack, ZStack with .frame() and .padding()) is simpler and safer—the layout engine handles sizing automatically. Use Auto Layout for UIKit legacy code; SwiftUI for new projects. For hybrids, UIViewRepresentable wraps UIKit views inside SwiftUI, though this sacrifices some declarative benefits.
  • How do you handle accessibility in iOS apps?
What interviewers look for: A strong answer demonstrates architectural decision-making grounded in production shipping: 'We migrated our payment flow to SwiftUI, but the custom animations required UIViewRepresentable wrapper—that's where UIKit still wins for complex transitions. Core business logic stayed in MVVM ViewModels to keep it testable.' A weak answer sounds like: 'SwiftUI is newer so it's better. MVVM sounds good. State management... I use @State for everything since it works.'

Networking, Persistence & App Store

Master URLSession, Codable, Core Data, keychain security, push notifications, and App Store submission requirements.

  • How do you use URLSession to make network requests in Swift?
  • Explain Codable and its benefits for JSON parsing.
  • What is the difference between Core Data and SwiftData?
    Sample Answer Guidance: Core Data is Apple's object-graph management with SQL persistence; models extend NSManagedObject, and you query via NSFetchRequest with NSPredicate filters. SwiftData (iOS 17+) simplifies this: models use Swift classes marked with @Model macro, and querying is more intuitive with Swift syntax. SwiftData is a lightweight wrapper over Core Data offering better developer experience. Choose SwiftData for new iOS 17+ projects; use Core Data for backwards compatibility or legacy codebases.
  • How do you securely store sensitive data (passwords, tokens) in iOS?
    Sample Answer Guidance: Use the Keychain (encrypted, OS-managed storage) never UserDefaults or files. Store tokens via SecItemAdd with kSecClass: kSecClassInternetPassword and kSecAttrServer to specify the service. For retrieval, SecItemCopyMatching returns the stored data. I use a wrapper like KeychainAccess (open-source) to simplify the API—it handles encoding/decoding automatically: Keychain(service: "myapp")["user_token"] = token. Never log sensitive values; consider @SecureString properties to prevent accidental exposure.
  • Explain push notifications in iOS. How do you implement remote notifications?
    Sample Answer Guidance: Request permission via UNUserNotificationCenter.current().requestAuthorization(options: [.alert, .sound, .badge]), then call UIApplication.shared.registerForRemoteNotifications() to get the APNs device token. In AppDelegate, implement didRegisterForRemoteNotificationsWithDeviceToken to capture and send the token to your backend. Set UNUserNotificationCenter.current().delegate in AppDelegate to intercept notifications. Handle received notifications in userNotificationCenter(_:willPresent:withCompletionHandler:), which lets you display alerts even when the app is active.
  • What is Xcode Cloud and how does it improve CI/CD for iOS?
  • Describe the App Store review process and common rejection reasons.
    Interviewer Insight: App Store questions test operational maturity—interviewers want to know if you've handled a real rejection and what you learned. Strong candidates discuss specific rejections: 'Our v1.0 was rejected for missing privacy policy—we didn't realise iOS required explicit GDPR compliance. Now I audit every release.' Weak answers treat App Store as a black box: 'Uh, you just submit and hope it works.'
  • How do you implement certificate pinning in URLSession?
    Sample Answer Guidance: Implement URLSessionDelegate and override urlSession(_:didReceive:completionHandler:) to validate the server's certificate against a pinned public key stored in your bundle. Extract the certificate from the challenge, compare its public key using SecCertificateCopyKey(), and call completionHandler(.useCredential:) or (.cancelAuthenticationChallenge:). Alternatively, use Alamofire's ServerTrustManager for simpler configuration. Trade-off: pinning increases security against MITM attacks but requires careful certificate rotation planning to avoid invalidating app pins.

How Interviewers Evaluate iOS Developer Candidates

Core iOS & Swift Knowledge (30%): ARC, memory management, optionals, protocols, generics, app lifecycle, and value vs. reference types. Do you explain clearly? Can you code examples?

Architecture & Code Design (25%): Do you understand MVVM, VIPER, testability, and dependency injection? Can you structure a feature scalably? Do you think about maintainability?

Problem-Solving & Debugging (20%): Can you debug using Instruments and Memory Graph? How do you approach unfamiliar problems? Do you ask clarifying questions or just code?

Practical Production Experience (15%): Have you shipped apps? Handled App Store rejection? Optimised performance? Integrated APIs? Real shipping experience shows maturity.

Communication & Collaboration (10%): Can you explain your reasoning clearly? Do you listen to feedback? Can you discuss trade-offs (SwiftUI vs. UIKit, MVVM vs. VIPER)?

Frequently Asked Questions

What is the difference between an iOS developer and a mobile developer?

An iOS developer specialises exclusively in Apple platforms (iPhone, iPad, watchOS, tvOS) using Swift, SwiftUI, and UIKit. A mobile developer may work across iOS, Android, and cross-platform frameworks (React Native, Flutter). iOS developers must master Apple's ecosystem—App Store guidelines, Xcode, Swift, ARC, Core Data—whereas mobile developers use more generalised mobile patterns.

Should I learn SwiftUI or UIKit?

Learn both. SwiftUI is modern and preferred for new projects (iOS 13+), but many production apps still use UIKit. Understanding UIKit gives you deeper knowledge of view hierarchies and controller lifecycle. Start with SwiftUI for greenfield projects, but master UIKit for legacy code and interviews—interviewers often probe your UIKit knowledge to assess fundamentals.

How do I prepare for the coding interview portion?

Practice LeetCode-style algorithms (arrays, strings, trees) in Swift. Expect live-coding questions about data structures or simple algorithms. More importantly, practise designing iOS-specific features: build a todo app with networking and persistence, refactor code to MVVM, implement a custom view controller transition, and optimise collection view scroll performance. Bring these projects to interviews.

What should I know about App Store submission?

Understand the review guidelines (content, privacy, functionality). Know how to build and upload apps via Xcode or App Store Connect. Familiarise yourself with common rejection reasons: missing privacy policy, unauthorised data collection, crashes on test devices, and misleading app metadata. Research successful appeals if your app is rejected. Privacy compliance—GDPR, App Tracking Transparency—is critical and often tested.

How important is performance optimisation knowledge?

Very important. Expect questions about memory management, scroll performance (collection/table views), app startup time, and battery usage. Know how to use Instruments (Allocations, Core Animation, Network) to identify bottlenecks. Mention specific optimisations you've done: image caching, lazy loading, reducing main-thread work, or using background queues.

What's the best way to demonstrate iOS expertise in interviews?

Bring a polished, complex iOS project you've built (not a tutorial clone). Walk through its architecture, discuss decisions (why MVVM?), explain memory management choices, and show profiling results. Discuss a production problem you've solved (app crash, App Store rejection, performance issue). Stay current: mention WWDC sessions you've watched, new Swift features you've explored, and experiments with SwiftUI or SwiftData.

How do I answer questions about unfamiliar APIs or frameworks?

Think aloud. Break down the problem: 'I haven't used that specific API, but here's my approach: (1) read the documentation, (2) understand the core concept, (3) check for delegate patterns or Combine integration.' Interviewers value problem-solving process, not rote memorisation. Reference similar frameworks you know (e.g., comparing URLSession to Alamofire) to show pattern recognition.

What recent Swift or iOS features should I know about?

Study Swift 5.9+ (macros for code generation), Swift 6 (actor-based concurrency improvements), SwiftUI updates (NavigationStack, observation framework), and iOS 18 features (AI integration APIs). Understand Combine and recent additions (Publisher.debounce, combineLatest improvements). Watch WWDC videos from the last two years. Mention one feature you've experimented with to show you stay current. Avoid claiming expertise in bleeding-edge features; discuss what you've actually used.
