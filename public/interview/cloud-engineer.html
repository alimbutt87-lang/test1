Cloud Engineer Interview Questions

Cloud engineer interviews test whether you can build and operate cloud infrastructure—not just draw architecture diagrams. Expect to configure VPCs, write Terraform, and troubleshoot networking issues live.

Cloud Engineer Specialisations

AWS Cloud Engineer

Specialises in designing and managing infrastructure on Amazon Web Services, including EC2, VPC, S3, IAM and AWS-specific tools like CloudFormation and CloudWatch.

Azure Cloud Engineer

Focuses on Microsoft Azure infrastructure including Virtual Machines, Virtual Networks, Azure Storage, Azure Entra ID (formerly Azure AD) and Infrastructure as Code using Bicep or ARM templates.

Multi-Cloud Engineer

Works across multiple cloud platforms (AWS, Azure, GCP) with skills in platform-agnostic tools like Terraform, Kubernetes and cloud cost optimisation across providers.

Typical Cloud Engineer Interview Process

1

Phone Screening (20-30 mins)

Initial screening covering background, experience with cloud platforms, and basic cloud concepts. Expect questions about your hands-on experience with compute and networking.

2

Technical Interview 1 (45-60 mins)

Deep dive into cloud infrastructure: VPC/VNet design, EC2/VM configuration, security groups, IAM policies. May include whiteboarding or architecture diagram scenarios.

3

Technical Interview 2 (45-60 mins)

Infrastructure as Code and automation: Terraform, CloudFormation or Bicep. Expect hands-on exercises writing IaC templates or debugging existing code.

4

Behavioural Interview (30-45 mins)

STAR format questions about problem-solving, incident response, team collaboration and handling production issues. Often overlaps with technical rounds.

5

Leadership/System Design (45-60 mins)

For mid-level and senior roles: design a complete cloud infrastructure solution, consider scalability, cost and security trade-offs.

Behavioural Questions

Cloud Engineer behavioural interviews assess your problem-solving, communication and incident management skills using the STAR method (Situation, Task, Action, Result).

  • Tell me about a time you had to troubleshoot a production outage in a cloud environment. What was the issue and how did you resolve it?
  • Describe a situation where you had to explain a complex cloud architecture decision to a non-technical stakeholder.
  • Tell me about a time you implemented Infrastructure as Code when your team previously managed infrastructure manually.
  • Describe your experience optimising cloud costs. What did you find and how much did you save?
  • Tell me about a disagreement you had with a colleague about cloud architecture or deployment strategy. How did you handle it?
  • Describe your most complex cloud infrastructure project. What made it challenging and what did you accomplish?
  • Tell me about a time you made a mistake with cloud infrastructure. How did you handle it and what did you learn?

Networking, Compute & Storage

Core competencies for Cloud Engineers: designing virtual networks, configuring compute instances, managing storage solutions and ensuring connectivity.

  • How would you design a VPC (or Virtual Network on Azure) for a multi-tier application with public and private subnets?
    Sample Answer Guidance: I'd create a VPC with two availability zones, each containing public subnets (with NAT gateways) for the load balancer tier and private subnets for application and database tiers. Public subnets use internet gateways with 0.0.0.0/0 routes, whilst private subnets route outbound traffic through NAT gateways for security patching. This pattern isolates databases from internet exposure whilst allowing secure outbound connections.
  • What's the difference between security groups and network ACLs in AWS? When would you use each?
  • Explain the purpose of NAT gateways and bastion hosts. When would you deploy each and why?
    Sample Answer Guidance: NAT gateways enable private instances to initiate outbound connections (for updates, API calls) while blocking inbound access—deployed in public subnets and used in production. Bastion hosts are hardened EC2 instances in public subnets that serve as secure jump hosts for administrative access to private instances, with strict security groups restricting SSH. Use NAT for scale, bastion for auditable admin access.
  • How do you choose between EC2 instance types for different workloads? What factors influence your decision?
  • Describe how you would configure an Application Load Balancer (ALB) or Azure Load Balancer for high availability across multiple availability zones.
    Sample Answer Guidance: I'd deploy an ALB with target groups across two+ AZs, enabling cross-zone load balancing in the target group settings. Configure health checks (HTTP 200 on /health with 30s intervals) to automatically deregister unhealthy instances. Use path-based routing rules to direct traffic to different services. Enable stickiness only if required, and use HTTPS listeners with ACM certificates to encrypt traffic.
  • What's your approach to choosing between S3 (or Azure Blob Storage) storage classes? How do you optimise for cost while maintaining performance?
  • How would you implement DNS failover and routing in AWS Route 53 (or Azure Traffic Manager) for disaster recovery?
    Sample Answer Guidance: I'd configure Route 53 failover routing with primary and secondary regions, each with health checks pointing to ALBs. Primary endpoints use failover policy to route to secondary only if health checks fail. Implement CloudWatch alarms to monitor endpoint health, and set low TTL values (30-60s) to enable rapid DNS propagation during failover. Test failover regularly using chaos engineering.
  • Explain the role of CloudFront (or Azure CDN) in your architecture. When would you implement a CDN and what performance benefits does it provide?
What interviewers look for: A strong answer sounds like: 'I'd use a private subnet with a NAT gateway for the application tier because these instances don't need inbound internet access, and I'd place the load balancer in the public subnet.' A weak answer sounds like: 'I'd put everything in a VPC with security groups.'

IAM, Security & Compliance

Cloud security is a critical responsibility: managing identities, enforcing least privilege, protecting data and ensuring compliance with regulatory frameworks.

  • Explain the principle of least privilege. How do you implement it in AWS IAM or Azure Entra ID and role-based access control?
  • What's the difference between AWS managed policies and customer managed policies? When would you create a custom IAM policy?
  • How do you handle secrets management in a cloud environment? Discuss AWS Secrets Manager, Azure Key Vault or similar tools.
    Sample Answer Guidance: I'd use AWS Secrets Manager to store database credentials, API keys and certificates with automatic rotation enabled—Terraform can provision this via aws_secretsmanager_secret. IAM policies grant specific roles permission to retrieve secrets, and CloudTrail logs all access. For ECS tasks, I'd pass secrets as environment variables through task role IAM permissions, avoiding hardcoding in application code or container images.
  • Describe your approach to implementing encryption at rest and in transit. What AWS or Azure services would you use?
    Sample Answer Guidance: For encryption at rest, I'd enable S3 server-side encryption with AWS KMS (not default S3 keys), RDS encryption using customer-managed keys, and EBS encryption for all volumes through Auto Scaling group settings. For transit, I'd enforce HTTPS/TLS 1.2+ on load balancers, use VPC endpoints for AWS service connections, and enable encryption on database connections. KMS key policies ensure only authorised roles can encrypt/decrypt.
  • What compliance frameworks are you familiar with (PCI-DSS, HIPAA, SOC 2)? How do you design infrastructure to meet these requirements?
  • How do you implement and monitor audit logging in AWS (CloudTrail) or Azure (Azure Monitor)? Why is this important?
  • Explain cross-account access in AWS. When would you use service-linked roles or assume roles across accounts?
    Sample Answer Guidance: I'd use cross-account assume roles for centralised logging (account A logs to account B's S3 bucket) and multi-account deployments. The source account role has a trust relationship allowing assume role from destination account, granting specific permissions—example: production account assumes a billing role in the shared cost centre account. Service-linked roles are auto-created by AWS services (e.g., Lambda for CloudWatch Logs) and shouldn't be manually managed.

Infrastructure as Code, Automation & Cost Management

Modern cloud operations rely on Infrastructure as Code (IaC) to provision infrastructure consistently and manage costs effectively at scale.

  • Compare Terraform, AWS CloudFormation and Azure Bicep. What are the advantages of each and how do you choose between them?
    Sample Answer Guidance: Terraform is platform-agnostic with cleaner HCL syntax and reusable modules—ideal for multi-cloud deployments. CloudFormation is AWS-native, tightly integrated with AWS services and IAM policies, but less portable. Bicep is Azure's simplified IaC language replacing ARM templates. I'd choose Terraform for multi-cloud flexibility and team familiarity, CloudFormation if locked into AWS ecosystem and native service support is critical.
  • How do you manage Terraform state files? Discuss remote state, state locking and security considerations.
    Sample Answer Guidance: I'd store remote state in S3 with DynamoDB for state locking (prevents concurrent apply conflicts), enabling versioning and server-side encryption with KMS. IAM policies restrict state file access—only CI/CD and authorised engineers. I'd avoid committing state to Git. For migrations, I'd use terraform import or backends to handle state transitions safely. Use terraform state show to audit sensitive values before sharing.
  • Write a Terraform module for provisioning an EC2 instance with security group and monitoring enabled. What best practices would you follow?
    Sample Answer Guidance: I'd structure a module with variables (instance_type, subnet_id, tags), outputs (instance_id, private_ip), and resources for security groups with ingress rules. Enable detailed CloudWatch monitoring (aws_cloudwatch_log_group), attach an IAM role for Systems Manager access, and pass user_data for agent installation. Use locals for standardised tags and avoid hardcoded values. The module should be reusable across environments with minimal variable changes.
  • Explain your approach to tagging strategy in cloud infrastructure. Why is tagging important for cost management and governance?
  • How do you implement auto-scaling policies in AWS (EC2 Auto Scaling Groups) or Azure (Virtual Machine Scale Sets)?
  • Describe your experience with monitoring and alerting. How do you use CloudWatch metrics and dashboards (or Azure Monitor) to detect issues?
  • What strategies do you use to optimise cloud costs? Discuss reserved instances, spot instances, compute scheduling and resource right-sizing.
    Sample Answer Guidance: I'd analyse AWS Cost Explorer to identify over-provisioned instances, then right-size compute using CloudWatch memory metrics. Mix reserved instances (3-year for stable workloads, 1-year for flexible) with spot instances for batch jobs and auto-scaling, saving 70-90% on compute. Implement scheduled shutdown for dev/test environments, use S3 Intelligent-Tiering for variable storage access, and enable EBS volume cleanup. Tag all resources for cost allocation and monthly cost reports.

Why Candidates Fail Cloud Engineer Interviews

Confusing Cloud Engineer with DevOps or Cloud Architect roles

Cloud Engineers focus on hands-on infrastructure implementation (VPCs, security groups, storage, IAM). DevOps Engineers specialise in CI/CD and deployment pipelines, while Cloud Architects design systems and plan migrations. Clarify your role's scope in preparation and in interviews.

Lacking hands-on experience with Infrastructure as Code

Interviewers expect you to write or debug actual Terraform, CloudFormation or Bicep code. Memorising syntax isn't enough—demonstrate practical experience provisioning real infrastructure. Build a small project on your own AWS or Azure account.

Poor understanding of networking fundamentals

VPCs, subnets, security groups and routing are core. Many candidates struggle with CIDR notation, routing tables or security group rules. Be prepared to design a multi-tier network and explain how traffic flows between layers.

Not discussing cost implications and optimisation

Cloud is consumption-based. Candidates who ignore cost in architectural discussions miss a key concern for hiring managers. Always discuss cost optimisation: right-sizing, reserved instances, storage tiers and cleanup policies.

Failing to ask clarifying questions

When given a scenario, rush straight to a solution. Instead, ask about requirements: scale, compliance, budget, team size. Good Cloud Engineers gather information before architecting. This demonstrates critical thinking and reduces costly mistakes.

What Interviewers Are Assessing

Hands-on Cloud Experience: Depth of practical experience with compute (EC2, VMs), networking (VPC, subnets), storage (S3, Blob) and monitoring. Can you provision infrastructure confidently?

Architectural Thinking: Do you understand trade-offs? Can you design for scalability, high availability and cost? Can you justify design decisions?

Infrastructure as Code Proficiency: Can you write, debug and optimise Terraform, CloudFormation or Bicep? Do you understand state management and version control?

Security and Compliance Mindset: Do you apply least privilege? Can you implement encryption, audit logging and compliance requirements? Is security a default, not an afterthought?

Problem-Solving Under Pressure: How do you approach troubleshooting? Can you debug infrastructure issues methodically? Do you ask good questions?

Communication and Collaboration: Can you explain technical decisions to non-technical stakeholders? Do you work well in teams? Can you document infrastructure?

Frequently Asked Questions

What is the difference between a Cloud Engineer and a DevOps Engineer?

Cloud Engineers focus on designing and managing cloud infrastructure—networking, compute, storage, security and cost optimisation. They provision resources using IaC tools like Terraform. DevOps Engineers specialise in CI/CD pipelines, deployment automation, container orchestration and release management. DevOps roles bridge development and operations, whilst Cloud Engineers are infrastructure specialists. Both roles may overlap, but hiring requires different skill sets. See our <a href="/interview/devops-engineer">DevOps Engineer interview guide</a> for deployment-focused preparation.

How do I prepare for a cloud engineering interview with no prior cloud experience?

Start with foundational courses: AWS Fundamentals, Azure Basics or Google Cloud Essentials. Create a free account and build projects: provision a web server, set up a VPC, configure security groups. Practise Infrastructure as Code with Terraform on a simple project. Study networking fundamentals (CIDR, subnets, routing). Join cloud communities, read case studies and follow cloud blogs. Most importantly, get hands-on experience—theory alone won't prepare you for technical rounds.

What cloud certifications are most valuable for Cloud Engineers?

AWS Certified Cloud Practitioner (foundational), AWS Solutions Architect Associate and AWS SysOps Administrator Associate are strong AWS credentials. For Azure, aim for Azure Administrator Associate and Azure Solutions Architect Expert. Google Cloud Associate Cloud Engineer is valued for GCP roles. Certifications validate knowledge and are often preferred by employers, but hands-on experience trumps credentials. Pursue certifications alongside real projects for maximum impact.

How important is multi-cloud experience for Cloud Engineer roles?

Single-cloud expertise (AWS or Azure) is often sufficient for most roles. However, multi-cloud skills differentiate you: experience with Terraform across providers, understanding platform-agnostic tools like Kubernetes, and knowledge of cost optimisation across clouds. Large enterprises increasingly adopt multi-cloud strategies to avoid vendor lock-in. If you've worked primarily on one platform, highlight transferable skills and express willingness to learn others.

What should I include in a portfolio or GitHub repository for Cloud Engineer interviews?

Create 2-3 real projects demonstrating your skills: a scalable web application on AWS or Azure (with VPC, load balancing, auto-scaling), Infrastructure as Code for a multi-tier architecture using Terraform, and a monitoring and alerting setup using CloudWatch or Azure Monitor. Include documentation explaining architecture, design decisions and cost considerations. Host these projects in GitHub with clear READMEs. Real, deployable code is far more impressive than theoretical knowledge.

How do I stay current with cloud technologies and interview trends?

Follow cloud blogs from AWS, Microsoft and Google. Subscribe to cloud newsletters like Last Week in AWS. Attend webinars and virtual conferences. Read whitepapers on Well-Architected Frameworks and best practices. Participate in cloud communities on Reddit or Discord. Practise hands-on with new services monthly. Interview prep resources on platforms like LeetCode and InterviewBit offer cloud-specific questions. Staying current shows genuine passion and adaptability.

What's the typical salary range for Cloud Engineers?

Cloud Engineer salaries vary by location, experience and cloud platform. In the UK, junior Cloud Engineers earn £30,000–£40,000, mid-level earn £45,000–£65,000 and senior positions reach £75,000+. In the US, salaries are higher: junior roles £50,000–£70,000, mid-level £80,000–£110,000 and senior £120,000+. Certifications, multi-cloud expertise and leadership experience boost earning potential. Specialised roles (security, cost optimisation) command premiums. Remote work availability typically offers competitive packages.

How do I handle 'I don't know' answers during interviews?

Honesty is valued. If you don't know an answer, say so confidently. Then, explain how you'd approach learning it: 'I haven't used that specific service, but I'd consult documentation, similar services I've used, and ask the team.' Show problem-solving thinking. Avoid guessing or making up answers—interviewers respect candidates who acknowledge knowledge gaps and demonstrate learning agility. Pivot to related experience you do have to show your capabilities.
